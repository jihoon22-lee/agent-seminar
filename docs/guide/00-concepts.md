# 0. 개념: 스킬, MCP, 플러그인

이 문서는 세미나 2장 "개념"을 글로 옮긴 것입니다. 처음 에이전트를 써 보는 분도 읽을 수 있게 썼습니다.
모든 내용은 **opencode 1.19.5** 기준입니다.

## 왜 확장이 필요한가

코딩 에이전트는 코드를 잘 읽고 잘 고칩니다. 하지만 다음은 모릅니다.

- 우리 팀이 정한 규칙: 커밋 메시지 형식, 리뷰 기준, 보고서 양식
- 에이전트 바깥에 있는 시스템: 장애 티켓, 팀 위키, 모니터링, 배포 도구
- 절대 하면 안 되는 일: 비밀 파일 읽기, 강제 푸시, 운영 DB 삭제

이걸 매번 프롬프트로 설명하면 같은 글을 계속 붙여 넣어야 하고, 사람마다 설명이 달라 결과가 들쭉날쭉합니다.
무엇보다 "하지 마"라는 프롬프트는 **부탁**일 뿐 강제가 아닙니다.
한 번 정리해서 에이전트에 붙여 두는 것이 확장입니다.

## 에이전트 루프와 세 가지 확장

에이전트는 다음을 반복합니다.

1. 사용자가 요청한다.
2. 모델이 다음에 무엇을 할지 고른다. 어떤 도구를 어떤 인자로 부를지 정한다.
3. opencode가 그 도구를 실제로 실행한다.
4. 결과를 모델에게 돌려준다. 2로 돌아간다.

| 확장 | 루프의 어디에 끼어드나 |
|---|---|
| **스킬** | 2단계에서 모델이 읽는 **지식**이 늘어난다. 모델이 필요하다고 판단할 때만 불러온다. |
| **MCP** | 2, 3단계에서 고를 수 있는 **도구**가 늘어난다. 도구는 opencode 바깥의 프로세스나 서버에서 실행된다. |
| **플러그인** | 3단계 **앞뒤에 코드가 끼어든다**. 모델의 판단과 상관없이 항상 실행된다. |

세 가지를 켜고 끄는 곳이 `opencode.json`과 `.opencode/` 폴더입니다. → [1. opencode.json](01-config.md)

## 스킬: 필요할 때 꺼내 보는 업무 매뉴얼

폴더 하나에 `SKILL.md`가 있으면 스킬입니다.

```
.opencode/skills/
└─ commit-message/
   ├─ SKILL.md          필수. 머리말(name, description) + 본문
   ├─ references/       필요할 때만 읽을 문서
   ├─ templates/        결과물 틀
   └─ scripts/          실행할 코드
```

```markdown
---
name: commit-message
description: 커밋 메시지를 팀 규칙에 맞게 쓴다. "커밋 메시지 써줘", "커밋해줘" 같은 요청에 사용한다.
---
# 커밋 메시지 규칙
1. 형식: type(scope): 요약 (50자 이내)
...
```

스킬은 세 단계로 나눠 읽힙니다. 이것을 **점진적 공개**라고 합니다.

1. **항상**: 모든 스킬의 `name`과 `description`만 모델에게 보입니다.
2. **필요할 때**: 모델이 `skill` 도구로 스킬을 열면 `SKILL.md` 본문이 대화에 들어옵니다.
3. **더 필요할 때**: 본문이 시키는 경우에만 참고 문서를 읽거나 스크립트를 실행합니다.

그래서 처음에 모델이 보는 것은 description뿐입니다. description이 모호하면 스킬은 쓰이지 않습니다.
작성 요령은 [2. 스킬](02-skills.md)에 있습니다.

`AGENTS.md`나 `instructions`도 모델이 읽는 문서라는 점은 같지만, **매 대화마다 항상** 들어갑니다.
짧고 늘 필요한 규칙은 AGENTS.md에, 길고 가끔 필요한 절차는 스킬에 두는 것이 기본 요령입니다.

## MCP: 에이전트에 도구를 꽂는 표준 규격

MCP(Model Context Protocol)는 에이전트(클라이언트)와 **도구 서버** 사이의 약속입니다.
USB-C처럼 단자 규격이 같기 때문에, 한 번 만든 서버를 여러 에이전트가 같이 씁니다.

- 서버는 별도 프로세스입니다. 어떤 언어로든 만들 수 있습니다.
- 서버가 줄 수 있는 것은 세 가지입니다.
  - **tools**: 모델이 호출하는 함수. 대부분의 서버는 이것만 제공합니다.
  - **resources**: 읽을 수 있는 문서나 데이터
  - **prompts**: 미리 만든 프롬프트 틀
- 속을 열어 보면 JSON-RPC 메시지를 주고받을 뿐입니다. `initialize`로 인사하고, `tools/list`로 목록을 받고, `tools/call`로 호출합니다.

### 로컬과 원격

| | 로컬 (`"type": "local"`) | 원격 (`"type": "remote"`) |
|---|---|---|
| 누가 실행 | opencode가 직접 프로세스를 띄운다 | 미리 떠 있는 서버에 접속한다 |
| 통신 | 표준 입출력(stdio) | HTTP (Streamable HTTP) |
| 설정 | `command` | `url`, 필요하면 `headers` |
| 인증 | 내 PC 권한 그대로 | 토큰 헤더 또는 OAuth |
| 업데이트 | 각자 PC에서 | 서버 한 곳에서 |
| 어울리는 곳 | 내 파일, 로컬 DB, 개인 도구 | 팀이 함께 쓰는 시스템 |

같은 서버 코드를 두 방식으로 모두 붙일 수 있습니다. → [3. MCP](03-mcp.md)

## 플러그인: opencode 안에 끼워 넣는 코드

`.opencode/plugins/`에 JS/TS 파일을 두면 opencode가 자동으로 로드합니다.
정해진 **훅**에 함수를 걸어 두면 opencode가 그때마다 호출합니다.

| 훅 | 할 수 있는 일 |
|---|---|
| `tool.execute.before` | 도구 실행 전에 검사, 인자 수정, 차단 |
| `tool.execute.after` | 실행 결과 기록, 후처리 |
| `shell.env` | 에이전트가 실행하는 셸 명령에 환경 변수 주입 |
| `event` | 세션 종료, 권한 요청 같은 이벤트 수신 |
| `tool` | 새 도구 추가 |
| `permission.ask`, `config`, `chat.*` | 권한 판단, 설정 변경, 메시지 가공 |

핵심은 **모델이 고르지 않는다**는 점입니다. 조건이 맞으면 항상 실행됩니다.
그래서 "반드시 지켜야 하는 규칙"과 "항상 일어나야 하는 자동화"에 씁니다.
대신 opencode 전용이라 다른 에이전트로 옮길 수 없습니다. → [4. 플러그인](04-plugins.md)

## 한 장으로 비교

| | 스킬 | MCP | 플러그인 |
|---|---|---|---|
| 한 줄로 | 필요할 때 읽는 매뉴얼 | 도구를 꽂는 표준 규격 | opencode 안의 확장 코드 |
| 정체 | 폴더 + `SKILL.md` | 별도 프로세스나 서버 | JS/TS 파일 |
| 누가 언제 쓰나 | 모델이 description을 보고 판단 | 모델이 도구를 고를 때 | opencode가 이벤트마다 항상 |
| 바꾸는 것 | 에이전트가 **아는 것** | 에이전트가 **할 수 있는 것** | opencode의 **동작 자체** |
| 컨텍스트 비용 | 평소엔 description만 | 도구 정의가 항상 들어간다 | 거의 없음 |
| 만드는 언어 | Markdown (+ 아무 언어 스크립트) | 아무 언어 | JavaScript / TypeScript |
| 다른 에이전트에서 | 대부분 그대로 | 표준이라 그대로 | opencode 전용 |

## 무엇을 쓸까

세 가지 질문으로 고릅니다.

1. **모델이 알아야 할 절차나 지식인가?** 커밋 규칙, 리뷰 기준, 보고서 양식, 분석 순서 → **스킬**
2. **에이전트 바깥의 시스템에 닿아야 하나?** 티켓 DB, 위키, 모니터링, 배포 API → **MCP 서버**
3. **모델 판단과 상관없이 항상 일어나야 하나?** 비밀 파일 차단, 감사 로그, 알림, 환경 변수 주입 → **플러그인**
   (단순히 특정 명령을 허용하거나 막는 정도라면 `permission` 설정 한 줄이 더 간단합니다.)

실제로는 섞어 씁니다. [`examples/04-combined/x2-incident-analysis`](../../examples/04-combined/x2-incident-analysis)는
MCP(티켓 조회) + 스킬(분석 절차) + 플러그인(감사 로그, 쓰기 범위 제한)을 하나의 작업에 엮은 예제입니다.
같은 기능을 세 가지 방식으로 각각 만들어 비교하는 [`x1-three-ways`](../../examples/04-combined/x1-three-ways)도 있습니다.
