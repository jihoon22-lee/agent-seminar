AGENTS.md는 항상 컨텍스트에 들어가므로 짧고 꼭 필요한 규칙만 둡니다. 길고 가끔 필요한 내용은 스킬로 빼는 것이 오늘의 첫 번째 요령입니다.

오늘은 가운데 세 줄이 주인공입니다. AGENTS.md와 스킬의 차이를 물어보시는 경우가 많은데, "항상 읽히나, 필요할 때만 읽히나"의 차이입니다.

스킬: 필요할 때 꺼내 보는 업무 매뉴얼

  • 폴더 하나에 SKILL.md가 들어 있으면 스킬이다
  • 머리말(frontmatter)의 description을 보고 모델이 쓸지 말지 판단한다
  • 본문에는 절차, 규칙, 예시를 쓴다
  • 필요하면 참고 문서, 템플릿, 스크립트를 같이 넣는다
  • 형식이 표준이라 다른 에이전트에서도 대부분 그대로 쓸 수 있다
.opencode/skills/ └─ commit-message/ ├─ SKILL.md 필수 ├─ references/ 필요할 때 읽을 문서 ├─ templates/ 결과물 틀 └─ scripts/ 실행할 코드
examples/01-skills/

스킬은 코드가 아니라 문서입니다. 모델이 읽고 따릅니다. 실행되는 무언가가 아니라는 점이 MCP, 플러그인과 가장 큰 차이입니다.

스킬은 세 단계로 나눠 읽힙니다

  1. 항상: 모든 스킬의 name과 description만 모델에게 보인다 스킬이 수십 개여도 부담이 작다
  2. 필요할 때: 모델이 skill 도구로 해당 스킬을 열면 SKILL.md 본문이 대화에 들어온다
  3. 더 필요할 때: 본문이 시키는 경우에만 references/ 문서를 읽거나 scripts/를 실행한다

그래서 description이 스킬의 전부입니다. 모델은 처음에 description만 보고 이 스킬을 쓸지 정합니다. 모호하게 쓰면 쓰이지 않습니다.

이 구조를 "점진적 공개"라고 부릅니다. 문서 전체를 매번 넣는 AGENTS.md와 달리, 정말 필요한 순간에만 비용을 냅니다.

description 작성법은 스킬 장에서 좋은 예와 나쁜 예로 실험한 결과를 보여 드립니다.

MCP: 에이전트에 도구를 꽂는 표준 규격

  • Model Context Protocol. 에이전트(클라이언트)와 도구 서버 사이의 약속
  • 서버는 별도 프로세스다. 어떤 언어로든 만들 수 있다
  • 서버가 줄 수 있는 것 세 가지
    • tools: 모델이 호출하는 함수 대부분 이것
    • resources: 읽을 수 있는 문서나 데이터
    • prompts: 미리 만든 프롬프트 틀
  • 표준이라 한 번 만든 서버를 여러 에이전트가 같이 쓴다

USB-C에 비유하면

기기(에이전트)와 주변기기(도구 서버)가 같은 단자 규격을 쓰기 때문에, 주변기기를 만드는 사람은 기기마다 따로 만들 필요가 없습니다.

티켓 시스템, DB, 팀 위키, 배포 도구처럼 에이전트 바깥에 있는 것에 손을 뻗게 해 줍니다.

MCP는 "능력"을 늘립니다. 스킬이 "어떻게 하라"는 지식이라면, MCP는 "이걸 할 수 있다"는 손발입니다.

속을 열어 보면 JSON 메시지를 주고받을 뿐입니다

  1. opencode가 서버를 시작하고 initialize로 인사한다
  2. tools/list로 도구 목록과 설명을 받는다
  3. 모델이 대화 중에 도구를 고른다
  4. opencode가 tools/call로 호출하고 결과를 모델에게 준다
examples/02-mcp/m1-stdio-minimal

SDK 없이 표준 라이브러리만으로 서버를 만들 수 있다는 것을 MCP 장에서 직접 보여 드립니다. 마법이 아니라 메시지 형식에 대한 약속이라는 점을 기억해 주세요.

모든 메시지에 "jsonrpc":"2.0"이 붙는데 화면에서는 줄였습니다. raw_session.py는 opencode 없이 서버를 직접 띄워 이 대화를 재현합니다. opencode 1.19.5는 initialize에서 2025-11-25 버전을 보냅니다.

플러그인: opencode 안에 끼워 넣는 코드

  • .opencode/plugins/에 JS/TS 파일을 두면 자동으로 로드된다
  • 정해진 훅에 함수를 걸어 두면 opencode가 때마다 부른다
  • 모델이 고르지 않는다. 조건이 맞으면 항상 실행된다
  • opencode 전용이다. 다른 에이전트로 옮길 수 없다

오늘 다루는 키는 이 정도입니다

  • $schema: 편집기가 자동 완성과 오류 표시를 해 준다
  • instructions: 항상 읽힐 규칙 문서
  • skills.paths: 기본 위치 밖의 스킬 폴더
  • mcp: 붙일 MCP 서버. 이름이 도구 이름 앞에 붙는다
  • plugin: 폴더 밖 플러그인. .opencode/plugins/는 적지 않아도 로드된다
  • permission: 도구별 허용, 확인, 거부

최상위 키 오타는 오류 없이 무시됩니다. "plugins", "permision", "skills": {"path": …}는 조용히 사라지고 opencode는 그냥 뜹니다. mcp 항목 안의 오타나 잘못된 값("bash": "maybe")만 시작을 막습니다. 적은 뒤에는 opencode debug config로 실제로 남았는지 보세요.

검사는 반쪽만 엄격합니다. mcp 서버 정의나 permission 값이 틀리면 시작이 막히지만, 최상위 키 이름이 틀리면 그 부분만 빠지고 아무 말 없이 뜹니다. 그래서 "플러그인을 등록했는데 안 불린다"면 plugins(복수형) 오타부터 의심하세요. $schema를 넣으면 편집기가 미리 빨간 줄을 그어 줍니다.

이 슬라이드는 opencode 1.19.5 형식입니다. 공식 문서에는 다음 버전 형식(mcp.servers, plugins)이 먼저 올라와 있는데, 1.19.5에서 plugins는 조용히 무시되는 키입니다. 문서를 볼 때 버전을 꼭 확인하세요.

권한 설정: 가장 간단한 안전장치

  • allow 바로 실행, ask 물어본 뒤 실행, deny 거부
  • 패턴은 나중에 쓴 규칙이 이긴다. 넓은 규칙을 먼저, 좁은 규칙을 뒤에
  • opencode run은 ask를 거절한다. --auto를 붙이면 ask는 허용, deny는 그대로 막는다
  • a && b는 부분마다 따로 판정한다

"rm *": "deny"는 git rm -f 파일을 못 잡습니다. 실험에서 실제로 파일이 지워졌습니다. 패턴은 명령 문자열 전체와 맞춰 보므로 rm *는 rm으로 시작하는 명령만 잡습니다. 더 촘촘히 막아야 하면 플러그인(P2)으로.

대화가 길어지면 opencode가 앞부분을 요약(압축)합니다. 이때 experimental.session.compacting 훅으로 꼭 남길 사실을 요약 프롬프트에 덧붙입니다.

  • output.prompt를 넣으면 프롬프트 전체가 바뀌고 context는 무시된다
  • 훅이 예외를 던지면 압축 자체가 실패한다. 반드시 감싸서 실패를 삼킬 것
  • 압축은 TUI의 /compact, 서버 API, 또는 컨텍스트가 가득 찰 때 일어난다
  • 이름 그대로 실험적 훅이다. 버전이 바뀌면 다시 확인할 것

만들기 전에, 만든 뒤에: 체크리스트

스킬

  • description에 무엇을과 언제, 사용자가 칠 문장을 넣었다
  • 본문은 짧게, 긴 내용은 references/로 나눴다
  • 계산과 집계는 스크립트에 맡겼다 (표준 라이브러리만)
  • 명령은 PowerShell과 bash에서 모두 도는 한 줄이다
  • opencode debug skill에 보인다
  • 다른 위치의 스킬과 이름이 겹치지 않는다

MCP 서버

  • 도구는 좁게, 이름과 설명은 모델이 고르기 쉽게
  • 결과는 작게. 목록은 개수 제한, 긴 본문은 요약
  • stdout에는 프로토콜만, 로그는 stderr
  • 입출력 UTF-8 (Windows cp949 대비)
  • 토큰은 {env:…}로, 원격은 127.0.0.1부터
  • opencode mcp list가 ✓ connected다

플러그인

  • 플러그인 함수만 export했다
  • 로드될 때 로그 한 줄을 남긴다
  • 차단 메시지에 이유와 대안이 있다
  • 판정 로직을 단위 테스트로 고정했다 (막을 것, 허용할 것)
  • 훅 안의 예외가 다른 기능을 망치지 않게 감쌌다
  • 단순 허용/거부라면 permission으로 충분한지 먼저 봤다
