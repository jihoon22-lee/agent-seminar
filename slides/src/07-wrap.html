만들기 전에, 만든 뒤에: 체크리스트

스킬

  • description에 무엇을과 언제, 사용자가 칠 문장을 넣었다
  • 본문은 짧게, 긴 내용은 references/로 나눴다
  • 계산과 집계는 스크립트에 맡겼다 (표준 라이브러리만)
  • 명령은 PowerShell과 bash에서 모두 도는 한 줄이다
  • opencode debug skill에 보인다
  • 다른 위치의 스킬과 이름이 겹치지 않는다

MCP 서버

  • 도구는 좁게, 이름과 설명은 모델이 고르기 쉽게
  • 결과는 작게. 목록은 개수 제한, 긴 본문은 요약
  • stdout에는 프로토콜만, 로그는 stderr
  • 입출력 UTF-8 (Windows cp949 대비)
  • 토큰은 {env:…}로, 원격은 127.0.0.1부터
  • opencode mcp list가 ✓ connected다

플러그인

  • 플러그인 함수만 export했다
  • 로드될 때 로그 한 줄을 남긴다
  • 차단 메시지에 이유와 대안이 있다
  • 판정 로직을 단위 테스트로 고정했다 (막을 것, 허용할 것)
  • 훅 안의 예외가 다른 기능을 망치지 않게 감쌌다
  • 단순 허용/거부라면 permission으로 충분한지 먼저 봤다

오늘 예제를 만들며 실제로 걸려 넘어진 것만 모았습니다. 각 항목 뒤에는 예제 하나씩이 있습니다. 예를 들어 "플러그인 함수만 export"는 P1을 만들다가, "UTF-8"은 M9에서 나왔습니다.

추천 순서 (1시간)

  1. S1a 커밋 메시지 스킬을 내 저장소에 복사해 본다
  2. M1 표준 라이브러리 서버를 띄우고 mcp list로 확인
  3. P1 .env 차단 플러그인을 켜고 막히는지 본다
  4. C1 demo.py로 설정 병합을 눈으로 본다
  5. 각 예제 README의 "직접 바꿔 보기"를 하나씩

모든 예제 폴더의 README는 같은 순서입니다. 무엇을 보여 주나, 실무에서는, 파일 구성, 따라 하기, 기대 결과, 동작 원리, 직접 바꿔 보기, 주의할 점.

check.py는 실제 opencode 설정을 건드리지 않습니다. 임시 폴더로 격리해서 실행하고 끝나면 지웁니다.

아는 것은 스킬로,
닿는 것은 MCP로,
지켜야 할 것은 플러그인으로.

그리고 셋을 켜고 끄는 곳은 opencode.json 하나입니다.

오늘 내용을 한 문장으로 줄이면 이렇습니다. 프롬프트에 매번 붙여 넣던 것이 있다면 그게 첫 번째 스킬 후보입니다.
