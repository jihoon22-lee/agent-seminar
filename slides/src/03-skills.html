스킬

Markdown 파일 하나에서 시작해 참고 문서, 스크립트, 결과물까지

10분. 단계별로 하나씩 키워 갑니다. 데모는 S1a(커밋 메시지). 시간이 남으면 S3a(로그 분석, 심화) 데모도 합니다.

스킬은 이렇게 키워 갑니다

단계구성예제언제
1SKILL.md 하나S1a커밋 메시지 S1b코드 리뷰 S1c장애 회고규칙과 절차를 글로 설명하면 충분할 때
2+ 참고 문서, 템플릿S2a작업 기록 S2bAPI 설계 S2cADR내용이 길어서 필요한 부분만 읽히고 싶을 때
3+ 스크립트S3a로그 분석 S3b릴리스 노트 S3c비밀값 검사계산, 집계, 파싱처럼 매번 같아야 하는 일
4+ 결과물 생성S4aHTML 리포트 S4b구조 다이어그램사람이 볼 파일을 만들어야 할 때

예제 이름 앞의 S1a 같은 번호가 레포의 폴더 이름과 같습니다. examples/01-skills/s1a-commit-message처럼 찾으시면 됩니다.

스킬을 두는 곳과 모델이 보는 것

위치범위
.opencode/skills/<이름>/SKILL.md이 프로젝트
~/.config/opencode/skills/내 PC 전체
"skills": {"paths": [...]}팀 공용 폴더
"skills": {"urls": [...]}정적 웹 서버

~/.claude/skills, ~/.agents/skills도 읽습니다. 다른 에이전트와 스킬을 같이 쓸 수 있습니다.

처음에 모델이 받는 것

  • 스킬마다 이름, description, 위치(경로)
  • 본문은 모델이 skill 도구로 열 때 들어온다
  • 열면 본문과 함께 스킬 폴더 경로와 폴더 안 파일 목록(일부)도 전달된다

그래서 본문에는 "어떤 파일이 있다"보다 "언제 어떤 파일을 읽어라"를 써야 합니다.

가짜 모델 서버로 opencode가 실제로 보낸 요청을 기록해서 확인했습니다. 위치 경로까지 모델에게 보이기 때문에 폴더 이름도 일종의 힌트가 됩니다.

확인 명령은 opencode debug skill. 이건 opencode가 읽은 것이고, 모델에게는 이름, 설명, 위치만 갑니다.

프롬프트에 스킬 이름을 쓰지 않았는데 스킬을 골랐고, 이슈 번호를 브랜치 이름에서 찾아냈습니다.

examples/01-skills/s1a-commit-message

체크리스트(이름, 오류 처리, 보안, 테스트, 로그)와 출력 형식을 스킬에 정해 두면, 누가 시켜도 같은 표가 나옵니다.

샘플 코드에 일부러 심은 결함 6개를 모두 찾고, 하나를 더 찾았습니다.

examples/01-skills/s1b-code-review

S1c장애 회고: 물어보며 쓰거나, 메모로 쓰거나

두 가지 방식을 한 스킬에

  • 대화형: 영향, 타임라인, 근본 원인(5 Whys), 잘한 점과 아쉬운 점, 후속 조치를 한 번에 하나씩 묻는다 (TUI에서)
  • 메모 기반: 장애 당시 메모를 주면 바로 문서를 만든다

담당자가 없는 조치는 지어내지 않고 확인 필요로 남기라고 스킬에 써 두었습니다.

examples/01-skills/s1c-postmortem

파일 이름의 날짜가 오늘이 아니라 메모에 적힌 장애 날짜입니다. 스킬에 "장애 발생일 기준"이라고 써 둔 규칙을 따른 결과입니다.

커밋 메시지 스킬

  1. → Skill "commit-message" 줄이 나오는지 본다
  2. 형식, 50자, Refs: #42를 확인한다
  3. sandbox\.opencode\skills\commit-message\SKILL.md의 규칙 하나를 바꾸고 다시 실행해 본다
examples/01-skills/s1a-commit-message

3번이 핵심입니다. sandbox는 별도의 git 저장소라서 원본 폴더의 SKILL.md가 아니라 sandbox 안의 복사본을 고쳐야 합니다. 규칙을 바꾸면 결과가 바로 바뀝니다. 팀 규칙이 바뀌면 이 파일 하나만 고치면 됩니다.

S2b목차만 두고, 필요한 문서만 읽게 하기

  • "주문 목록 API 설계해줘" → naming.md, pagination.md만 읽으면 된다
  • 참고 문서에는 확인 가능한 규칙을 둔다. 예: 커서는 pg1_로 시작, limit 기본 25, 최대 100
  • 결과에 이 규칙이 나오면 문서를 읽었다는 증거다

본문이 짧을수록 스킬을 여는 비용이 작습니다. 긴 규칙은 쪼개서 "언제 읽을지"를 표로 주세요.

examples/01-skills/s2b-api-design

이 예제의 실제 모델 확인은 무료 모델 한도 때문에 마치지 못했습니다. 가짜 모델로 opencode가 스킬 본문과 파일 목록을 전달하는 것까지는 확인했습니다.

S2a실제로 쓰던 스킬을 opencode로 옮기며 바꾼 것

workthrough는 작업이 끝날 때마다 무엇을 왜 바꿨는지 기록 문서를 남기는 스킬입니다(MIT 라이선스). 발표자가 매일 쓰는 스킬을 그대로 가져왔습니다.

workthrough/ ├─ SKILL.md 규칙과 절차 ├─ TEMPLATE.md 문서 틀 ├─ EXAMPLES.md 예시 모음 ├─ LICENSE.txt 원본 그대로 └─ NOTICE.md 출처와 바꾼 점

바꾼 점

  • 본문에 통째로 들어 있던 50줄짜리 템플릿을 빼고 "문서를 쓸 때 TEMPLATE.md를 읽는다"로 바꿨다
  • "작업 뒤 자동으로 문서화한다"는 문장을 "요청받거나 작업을 마친 직후에 쓴다"로 고쳤다. 스킬은 저절로 실행되지 않는다. 모델이 고르거나 사용자가 부른다
  • description에 한국어 요청 문구를 덧붙였다

라이선스와 바꾼 내용은 NOTICE.md에 남겼습니다. 남의 스킬을 가져올 때의 예의입니다.
