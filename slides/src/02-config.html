opencode.json

설정 파일은 어디에 두고, 여러 개면 어떻게 합쳐지는가

7분. 스킬, MCP, 플러그인 모두 결국 이 파일과 폴더 구조로 켭니다. 그래서 먼저 봅니다.

설정은 세 곳에 둘 수 있습니다

범위위치이럴 때
전역~/.config/opencode/opencode.json
Windows: %USERPROFILE%\.config\opencode\opencode.json		나만 쓰는 설정, 모든 프로젝트 공통
프로젝트<프로젝트>/opencode.json팀이 git으로 공유하는 설정
프로젝트 (폴더형)<프로젝트>/.opencode/opencode.json스킬, 플러그인과 한 폴더에 모으고 싶을 때

스킬과 플러그인 폴더도 같은 범위를 따릅니다.

~/.config/opencode/skills/ ↔ .opencode/skills/
~/.config/opencode/plugins/ ↔ .opencode/plugins/

opencode는 실행한 폴더부터 git 루트까지 올라가며 설정을 찾습니다. 그래서 프로젝트 하위 폴더에서 실행해도 루트의 설정이 적용됩니다.

examples/00-config/c1-scope-merge

팀이 공유할 것은 프로젝트에, 개인 취향은 전역에. 토큰 같은 비밀값은 어디에도 직접 쓰지 않고 환경 변수로 넘깁니다. 잠시 뒤에 봅니다.

오늘 다루는 키는 이 정도입니다

  • $schema: 편집기가 자동 완성과 오류 표시를 해 준다
  • instructions: 항상 읽힐 규칙 문서
  • skills.paths: 기본 위치 밖의 스킬 폴더
  • mcp: 붙일 MCP 서버. 이름이 도구 이름 앞에 붙는다
  • plugin: 폴더 밖 플러그인. .opencode/plugins/는 적지 않아도 로드된다
  • permission: 도구별 허용, 확인, 거부

opencode 1.19.5 기준 형식입니다. 공식 문서에는 다음 버전 형식(mcp.servers, plugins)이 먼저 올라와 있으니 버전을 확인하세요.

설정은 엄격하게 검사됩니다. 키 이름이 틀리면 opencode가 시작되지 않습니다. $schema를 꼭 넣으세요.

여러 파일은 덮어쓰지 않고 합쳐집니다

① 전역~/.config/opencode/
›
② OPENCODE_CONFIG로 지정한 파일
›
③ 프로젝트opencode.json
›
④ 프로젝트.opencode/opencode.json
›
⑤ OPENCODE_CONFIG_CONTENT환경 변수 속 JSON
  • 오른쪽으로 갈수록 우선한다. 같은 키만 오른쪽 값이 이긴다
  • 다른 키는 모두 살아남는다. 전역에 둔 MCP와 프로젝트의 MCP가 둘 다 켜진다
  • OPENCODE_CONFIG 파일은 프로젝트 설정보다 약하다 헷갈리기 쉬운 지점

직접 실험해서 확인한 순서입니다. 다섯 가지 경우를 차례로 돌려 보는 demo.py가 예제에 있습니다.

examples/00-config/c1-scope-merge

이 순서는 1.19.5에서 같은 키를 다섯 군데에 넣고 하나씩 빼 보며 확인했습니다. 문서만 믿지 말고 debug config로 확인하는 습관을 권합니다.

지금 무엇이 적용됐는지 확인하는 명령

"설정했는데 안 된다"의 대부분은 이 네 명령으로 원인이 보입니다.

  • 키 오타, 다른 파일이 덮어쓴 값 → debug config
  • 스킬이 안 보인다 → debug skill
  • MCP 서버가 안 붙는다 → mcp list

설정은 시작할 때 한 번만 읽습니다. 고친 뒤에는 opencode를 다시 실행하세요.

데모 중에 막히면 저도 이 명령부터 칩니다.

비밀값은 설정 파일에 직접 쓰지 않습니다

  • {env:이름}: 환경 변수 값으로 바뀐다
  • {file:경로}: 파일 내용으로 바뀐다
  • ${이름}처럼 셸 문법은 바뀌지 않는다
  • environment: 로컬 MCP 서버 프로세스에 넘길 환경 변수

debug config에서 environment 값은 ***로 가려져 나옵니다. 화면 공유 중에도 안전합니다.

examples/00-config/c2-variables

이렇게 하면 opencode.json은 그대로 git에 올리고, 토큰은 각자 환경 변수로 넣습니다. 팀원 모두 같은 파일을 씁니다.

실전 사례: 사용자 설정을 건드리지 않고 MCP 붙이기

agent-browser는 크롬을 opencode 에이전트가 조작하게 해 주는 프로젝트입니다. 브라우저 MCP 서버를 붙여야 하는데, 사용자의 전역 설정 파일은 고치고 싶지 않았습니다.

  • 자기가 띄우는 opencode 프로세스에만 OPENCODE_CONFIG_CONTENT로 mcp.browser를 넣는다
  • 우선순위가 가장 높아서 기존 모델, 인증, 다른 MCP 설정은 그대로 두고 덧씌워진다
  • MCP 서버에 필요한 값(WSL 연결 정보)은 environment로 넘긴다

github.com/jihoon22-lee/agent-browser

examples/00-config/c3-config-content-overlay

도구를 배포하는 입장이라면 이 패턴이 유용합니다. 설치 스크립트가 사용자의 설정 파일을 고치면 충돌과 복구 문제가 생기는데, 실행할 때만 덧씌우면 그런 문제가 없습니다.

내 설정을 망치지 않고 실험하는 법

  • XDG_CONFIG_HOME, XDG_DATA_HOME, XDG_CACHE_HOME, XDG_STATE_HOME을 임시 폴더로 바꾸면 전역 설정, 세션 기록, 캐시가 모두 격리된다
  • OPENCODE_DISABLE_EXTERNAL_SKILLS=1: 다른 에이전트용 스킬 폴더(~/.claude/skills, ~/.agents/skills)를 읽지 않는다
  • OPENCODE_DISABLE_AUTOUPDATE=1: 실험 중 자동 업데이트를 막는다

이 레포의 모든 예제 검사(check.py)는 이렇게 격리한 상태에서 돌아갑니다.

examples/00-config/c4-isolated-testing

스킬이나 플러그인을 만들 때 내 평소 설정과 섞이면 "왜 되지?"와 "왜 안 되지?"를 구분할 수 없습니다. 격리가 개발의 기본입니다.

권한 설정: 가장 간단한 안전장치

  • allow 바로 실행, ask 물어본 뒤 실행, deny 거부
  • 패턴은 나중에 쓴 규칙이 이긴다. 넓은 규칙을 먼저, 좁은 규칙을 뒤에
  • opencode run --auto는 ask를 자동으로 허용하지만 deny는 그대로 막는다

패턴으로 충분하면 permission, 조건이 복잡하거나 기록과 알림까지 필요하면 플러그인. 둘 다 플러그인 장에서 비교합니다.

examples/00-config/c5-permissions

스킬이나 MCP 도구도 permission으로 제어할 수 있습니다. 예를 들어 특정 스킬은 deny, 특정 MCP 도구는 ask.
