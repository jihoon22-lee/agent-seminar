# 장애 분석 리포트 절차

티켓 데이터는 `tickets_*` MCP 도구(읽기 전용)로만 읽는다. 추측으로 숫자를 만들지 말고, 모든 주장에는 티켓 ID나 배포 ID를 붙인다.

## 1단계 - 기간 정하기
`tickets_week_range` 를 호출한다. 응답의 `from`/`to` 가 "이번 주", `today` 가 리포트 날짜다.
비교용으로 `offset=1` 도 한 번 호출해 지난주 범위를 얻는다.

## 2단계 - 통계
대상 서비스에 대해 `tickets_ticket_stats` 를 이번 주와 지난주 각각 호출한다. 총 건수, P1/P2 건수,
피크 일자, 구성요소별 건수, 평균 해결 시간을 비교한다. 지난주 대비 증가가 뚜렷한 지점을 찾는다.

## 3단계 - 관련 티켓과 배포
1. `tickets_search_tickets` 로 피크 구간의 P1/P2 티켓과 가장 많은 구성요소의 티켓을 본다.
2. 대표 티켓 한두 건은 `tickets_get_ticket` 으로 본문과 직전 배포를 확인한다.
3. `tickets_recent_deploys` 로 이번 주 배포를 보고, 티켓이 급증한 시각과 배포 시각을 맞춰 본다.
4. 다른 서비스 티켓(`tickets_list_services` 로 확인)에 같은 서비스가 원인으로 언급되는지 `keyword` 로 검색한다.

## 4단계 - 가설
가설을 2~4개 세운다. 각 가설마다 근거(티켓/배포 ID), 확신도(높음/중간/낮음), 확인 방법을 적는다.
배포와 무관한 외부 요인(예: 협력사 지연)도 후보에 넣는다. 근거가 약하면 약하다고 쓴다.

## 5단계 - 리포트 저장
1. `.opencode/skills/incident-analysis/templates/report.md` 를 읽는다.
2. 템플릿의 `{{...}}` 와 빈 칸을 채워 `reports/<today>-<service>.md` 로 저장한다. 예: `reports/2026-11-17-payment.md`
3. 파일은 반드시 `reports/` 폴더 안에만 쓴다. 다른 곳에 쓰려 하면 플러그인이 막는다.
4. 마지막 답변에는 저장한 경로와 핵심 결론 3줄만 적는다.
