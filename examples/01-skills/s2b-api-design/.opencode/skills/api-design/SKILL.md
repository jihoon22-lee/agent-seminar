# 팀 API 설계 규칙 (라우터)

이 파일은 목차 역할만 한다. 구체적인 규칙은 `references/` 폴더의 파일에 있고, **규칙은 읽은 파일에 적힌 것만 따른다.** 기억이나 일반 상식으로 대신하지 않는다.
경로는 이 SKILL.md 파일이 있는 폴더 기준이다.

## 어떤 파일을 언제 읽는가

| 설계 중인 것 | 읽을 파일 |
| --- | --- |
| 새 리소스·엔드포인트·JSON 필드를 만든다 (**모든 설계에서 먼저**) | `references/naming.md` |
| 여러 건을 돌려주는 목록·검색 API가 있다 | `references/pagination.md` |
| 오류 응답, 상태 코드, 검증 실패를 다룬다 | `references/errors.md` |
| 경로 접두사, 호환성, 폐기 일정을 다룬다 | `references/versioning.md` |
| 로그인, 토큰, 권한(누가 호출할 수 있는지)을 다룬다 | `references/auth.md` |

규칙:

1. 요청에 해당하는 행의 파일만 읽는다. 목록 조회 API를 설계하면서 인증 이야기가 없다면 `auth.md`는 읽지 않는다.
2. 한 요청이 여러 행에 해당하면 해당하는 파일을 모두 읽는다. (예: "주문 목록 조회 API, 페이지네이션 포함" → naming + pagination. 오류 응답을 따로 언급했다면 errors도.)
3. 파일을 읽은 뒤 규칙과 충돌하는 부분은 규칙을 우선한다. 사용자가 규칙을 어기자고 하면 어떤 규칙인지 밝히고 확인한다.

## 설계 결과의 형식

1. 엔드포인트 표: `메서드 | 경로 | 설명`
2. 요청 예시(쿼리 문자열 또는 JSON)
3. 성공 응답 예시(JSON)
4. 적용한 규칙: 어느 reference 파일의 어느 규칙을 적용했는지 한 줄씩 (예: `pagination.md: limit 최대 100`)

설계만 한다. 사용자가 구현을 요청하지 않는 한 코드는 작성하지 않는다.
