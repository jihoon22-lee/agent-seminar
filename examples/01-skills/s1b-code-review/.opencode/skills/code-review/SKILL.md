# 팀 코드 리뷰 체크리스트

리뷰 대상 파일을 끝까지 읽은 뒤, 아래 다섯 영역을 **모두** 훑는다. 영역마다 문제가 없더라도 건너뛰지 말고 확인한다.
리뷰는 코드를 읽기만 한다. 사용자가 고쳐 달라고 하기 전에는 파일을 수정하지 않는다.

## 체크리스트

### 1. 보안 (대부분 치명)

- SQL을 문자열 포매팅(`f"..."`, `%`, `.format()`, `+`)으로 만들어 실행한다 → SQL 인젝션. 파라미터 바인딩(`?`, `%s`)을 쓰게 한다.
- 비밀번호, API 키, 토큰이 소스에 하드코딩되어 있다 → 환경 변수나 비밀 저장소로 옮기고, 이미 커밋되었다면 폐기·재발급한다.
- 사용자 입력으로 파일 경로를 만든다 → 경로 탐색(path traversal, `../`). 기준 폴더를 resolve한 뒤 그 안에 있는지 검사한다.
- 사용자 입력을 그대로 셸 명령, `eval`, `pickle` 등에 넘긴다.

### 2. 에러 처리

- 맨 `except:` 또는 `except Exception: pass`처럼 오류를 삼킨다 → 구체적인 예외만 잡고 기록하거나 다시 던진다.
- 실패했는데 성공처럼 `None`, `0`, 빈 값을 돌려준다.
- 파일, 연결, 트랜잭션을 닫지 않는다(`with`를 쓰지 않음).

### 3. 이름 짓기

- 한 글자 이름(`d`, `x`, `l`), 의미 없는 이름(`data`, `tmp`, `proc`, `do_it`).
- 함수 이름이 실제 동작과 다르다(`get_`인데 DB에 쓴다 등).
- 같은 개념을 파일 안에서 다른 이름으로 부른다.

### 4. 테스트

- 변경한 함수에 대응하는 테스트가 있는가. 없으면 어떤 케이스가 필요한지 적는다(정상, 경계값, 오류 입력).
- 보안·오류 처리 로직은 테스트 없이 두지 않는다.

### 5. 로깅

- 개인정보·비밀(카드 번호, 비밀번호, 토큰)을 로그나 `print`로 남긴다 → 마스킹하거나 남기지 않는다.
- 오류가 났는데 아무 기록도 남기지 않는다. 반대로 정상 흐름마다 `print`로 디버그 출력을 남긴다.
- `print` 대신 `logging`을 쓴다.

## 심각도 기준

| 등급 | 기준 | 머지 |
| --- | --- | --- |
| 치명 | 보안 취약점, 데이터 손실·오염, 비밀 노출 | 반드시 고치고 머지 |
| 주의 | 오류 삼킴, 테스트 부재, 개인정보 로깅처럼 곧 사고가 될 수 있는 것 | 고치거나 이유를 남기고 머지 |
| 제안 | 이름, 가독성, 사소한 개선 | 선택 |

## 출력 형식 (반드시 이 순서)

1. 심각도 표. 열은 `심각도 | 위치 | 문제 | 제안`으로 고정하고, 치명 → 주의 → 제안 순으로 정렬한다. 위치는 `파일:줄번호`로 쓴다.

```
| 심각도 | 위치 | 문제 | 제안 |
| --- | --- | --- | --- |
| 치명 | app.py:12 | ... | ... |
```

2. `## 요약` 제목 아래에 세 줄 이내로 쓴다: 등급별 개수, 머지 가능 여부, 가장 먼저 고칠 한 가지.
3. 표에 넣을 문제가 하나도 없으면 표 대신 "체크리스트 다섯 영역에서 문제를 찾지 못했습니다"라고 쓴다.

문제를 찾을 때는 줄 번호를 확인하고, 코드에 없는 문제를 추측해서 적지 않는다.
