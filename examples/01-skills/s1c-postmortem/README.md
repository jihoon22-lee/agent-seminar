# S1c 장애 포스트모템 스킬

> 구성: SKILL.md 한 장(스크립트 없음) + 가상의 장애 메모 | 난이도: ★★☆ | 필요: opencode 1.19.5 | 슬라이드: 스킬 — 같은 스킬, 두 가지 모드

## 무엇을 보여 주나

장애 회고(포스트모템)는 매번 형식이 들쭉날쭉해지기 쉬운 문서다. 이 스킬은 영향, 타임라인, 근본 원인(5 whys), 잘된 점·아쉬운 점, 담당자와 기한이 있는 액션 아이템이라는 틀을 고정한다.
하나의 스킬이 상황에 따라 두 가지로 동작한다. 사람과 대화하며 한 번에 질문 하나씩 던져 채우는 **대화형 모드**와, 이미 있는 메모를 읽어 문서를 만들어 내는 **문서 모드**다. 모드를 고르는 규칙도 SKILL.md에 적혀 있다.

## 실무에서는

- **장애 직후의 메모를 문서로**: 장애 대응 중에는 채팅방과 대시보드에 흩어진 메모가 전부다. 그 메모를 `notes/`에 붙여 넣고 "포스트모템 써줘"만 하면 초안이 나온다. 사람은 초안의 `확인 필요`만 채우면 된다.
- **회고 회의 진행**: 대화형 모드는 회의에서 진행자 역할을 한다. 영향 → 타임라인 → 원인 → 개선 순서로 한 가지씩 물으니 회의가 한 주제에 머문다.
- **비난 없는 문서(blameless)**: 사람 이름을 역할로 바꿔 쓰고, 마지막 "왜"가 사람의 실수가 아니라 장치·프로세스의 빈틈에 닿도록 규칙을 넣었다. 문서 품질의 일관성이 사람의 숙련도에 덜 기대게 된다.
- **액션 아이템이 사라지지 않게**: 담당 역할과 YYYY-MM-DD 기한이 없는 항목을 허용하지 않으므로, 회고 후 "누가 언제까지"가 비어 있는 문서가 줄어든다. 기한이 없으면 사건일 기준 7일/30일로 제안하고 `(제안)`을 붙여 확정과 구분한다.
- **포스트모템은 저장소에 커밋하지 않는 팀도 있다.** 이 예제는 생성물이 `postmortems/`에 쌓이도록 하고 `.gitignore`로 제외했다. 실제 팀에서는 이 줄을 지우고 문서를 공유 저장소에 커밋하면 된다.

## 파일 구성

```
s1c-postmortem/
├── README.md
├── check.py                                  자동 검증
├── fake_llm.py                               가짜 LLM 서버. check.py 가 모델 없이 opencode 의 요청을 기록·재현하는 데 씀
├── .gitignore                                postmortems/ 제외 (생성물)
├── notes/incident-notes.md                   가상 장애의 날것 메모 (이름 없음, 역할 A~F)
└── .opencode/skills/postmortem/
    └── SKILL.md                              두 모드 + 문서 형식 + 저장 규칙
```

실행 후에는 `postmortems/2026-08-14-<slug>.md`가 생긴다(git에는 올라가지 않음).

## 따라 하기

평소 쓰는 모델로 실행하면 됩니다. 모델 설정이 없다면 `-m opencode/big-pickle`(무료 모델)을 붙이세요.

### A. 문서 모드: 메모로 문서 만들기

PowerShell:
```powershell
cd examples\01-skills\s1c-postmortem
opencode run "notes/incident-notes.md 로 포스트모템 작성해줘"
Get-Content -Encoding UTF8 postmortems\*.md
```

Linux bash:
```bash
cd examples/01-skills/s1c-postmortem
opencode run "notes/incident-notes.md 로 포스트모템 작성해줘"
cat postmortems/*.md
```

무료 모델을 쓰려면 `opencode run -m opencode/big-pickle --auto "..."`.
대화창에서 하려면 `opencode`를 실행한 뒤 같은 문장을 입력한다.

### B. 대화형 모드: 질문을 받으며 쓰기

`opencode`(대화창)를 실행하고 입력한다.

```
어제 있었던 장애를 포스트모템으로 같이 써줘. 질문하면서 진행해줘.
```

에이전트가 질문을 하나만 던지면 답하고, 다음 질문이 나오는 식으로 6단계(영향 → 타임라인 → 원인 → 잘된 점 → 아쉬운 점 → 액션 아이템)를 진행한 뒤 파일을 쓴다. 모르는 항목은 "모르겠다"고 답하면 `확인 필요`로 남는다.

## 기대 결과

### A. 문서 모드 (`opencode/big-pickle`로 실행한 실제 출력)

````
`postmortems/2026-08-14-order-api-pool-exhaustion.md`

- 새 요약 쿼리가 인덱스 없이 조인해 응답이 지연됐고, 요청 적체로 커넥션 풀이 고갈됐다.
- 14:05~15:26 약 81분간 주문 목록 조회 요청의 약 11%(4,200건)가 실패했고, v3.11 롤백으로 복구했다.
- 성능 테스트 게이트 부재와 풀·에러 알림 미탐지가 주요 원인이며, 담당·기한이 있는 액션 아이템 5건을 정리했다.

`확인 필요` 3건(심각도, 매출 영향, 고객지원 규칙 담당자)이 남아 있다.
````

생성된 `postmortems/2026-08-14-order-api-pool-exhaustion.md`의 일부:


눈여겨볼 점:

- 파일 이름의 날짜는 **오늘이 아니라 메모에 적힌 장애 날짜**(2026-08-14)다. 스킬이 그렇게 지시했다.
- 메모에서 "담당 미정"이던 항목은 담당자를 지어내지 않고 `확인 필요`로 남았다. 메모에 "이번 주 내", "한 달 안"으로만 적힌 기한은 날짜로 바꾸면서 `(제안)`을 붙였고, `2026-08-21까지`로 명시된 항목은 그대로 두었다.
- 메모의 `당직자 B`, `리드 C` 같은 표기는 문서에서 역할(당직자)로 바뀌었다.

### B. 대화형 모드

**실제 모델로는 확인하지 못했다.** 이 모드를 시험해 보려던 시점에 무료 모델 사용량이 소진되어 응답이 오지 않았다. 아래는 SKILL.md가 지시하는 동작이며, 직접 실행해 확인해 보자.

- 첫 응답은 질문 **하나**여야 한다(영향: "무슨 일이 있었나요? 누가, 무엇이, 얼마나 오래 영향을 받았나요?").
- 답할 때마다 한 문장으로 되짚고 다음 질문(타임라인 → 원인 → 잘된 점 → 아쉬운 점 → 액션 아이템)으로 넘어간다.
- `opencode run`은 한 번 답하고 끝나므로, 대화형 모드는 `opencode` 대화창에서 시험한다.

모델 없이 확인되는 것은 `check.py`가 가짜 LLM 서버로 보여 주는 두 가지다. 모델의 시스템 프롬프트에는 스킬의 이름과 description만 있고, 두 모드의 규칙은 스킬을 불러온 뒤 도구 결과로 전달된다.

## 동작 원리

1. **발견과 로드**: `opencode debug skill`에 `postmortem`이 보이고, 프롬프트가 description의 "포스트모템 써줘" 같은 문구와 맞으면 모델이 `skill` 도구로 본문을 읽는다(`→ Skill "postmortem"`).
2. **모드 결정**: 본문 첫머리의 표가 판단 기준이다. 자료 파일이 지정되었거나 질문에 답해 줄 사람이 없으면 문서 모드, 자료 없이 대화로 시작하면 대화형 모드. 같은 프롬프트 형식("~로 포스트모템 작성해줘")이라도 자료 유무에 따라 동작이 갈린다.
3. **문서 모드**: 모델은 `Read`로 메모를 읽고, 규칙대로 시간순으로 재구성하고, `Write`로 `postmortems/YYYY-MM-DD-<slug>.md`를 쓴다. `Write` 호출은 실행 기록에 `← Write <경로>`로 나타난다.
4. **사실 지어내기 방지**: 본문에 "노트에 없는 사실은 `확인 필요`로 적는다"는 규칙이 있다. 메모에 없는 심각도와 매출 영향이 그대로 `확인 필요`로 남은 것이 그 결과다.
5. **`opencode run`의 한계**: `opencode run`은 한 번 답하고 끝나는 비대화형 실행이다. 질문하고 답을 기다리는 대화형 모드는 `opencode` 대화창에서 써야 제맛이 난다.

## 직접 바꿔 보기

- `notes/incident-notes.md`를 다른 사건으로 바꿔 보자(날짜를 바꾸면 파일 이름의 날짜가 바뀐다). 심각도를 메모에 한 줄 추가하면 `확인 필요`가 사라지는지 보자.
- 문서 형식에 `## 재발 방지 검증` 절(액션 아이템 완료 후 어떻게 확인할지)을 추가하고 다시 실행해 보자.
- SKILL.md의 기한 규칙을 "재발 방지 핵심 항목 7일 / 나머지 30일"에서 "14일 / 60일"로 바꾸면 `(제안)` 날짜가 따라 바뀐다.

## 주의할 점 / 문제 해결

- **`postmortems/`는 git에 올라가지 않는다.** 이 예제의 `.gitignore`가 제외한다. 결과 파일이 `git status`에 보이지 않는 것은 정상이다.
- **같은 날짜·같은 slug를 다시 만들면** 스킬 규칙에 따라 덮어쓰지 않고 `-2`를 붙인 파일이 생긴다. 다시 실행해 결과를 비교하려면 `postmortems/`를 지우고 실행하자.
- **`.opencode/`가 있는 폴더에서는** opencode가 시작할 때 `@opencode-ai/plugin`을 npm에서 설치하려 시도하고, 성공하면 `.opencode/` 안에 `package.json`, `node_modules/`, `.gitignore`가 생긴다(모두 git에서 제외). 이 예제에는 플러그인(`.opencode/plugins/*.js`)이 없어서, 레지스트리에 닿지 않는 환경에서도 눈에 띄는 멈춤은 없었다(연결을 거부하는 레지스트리로 측정: `opencode debug skill` 약 2초, `opencode run` 약 4초. TUI는 확인하지 못했다). 설치 시도 자체는 일어난다. 같은 환경에서 `.opencode/plugins/*.js`가 있는 폴더(P1~P8 등)는 시작할 때마다 약 70초 멈춘다(새 환경의 맨 처음 시작은 약 130초). 패키지 미러를 지정하는 방법은 [P6 README](../../03-plugins/p6-custom-tool/README.md#npm-자동-설치와-레지스트리패키지-미러)에 있다.
- **메모는 가상이다.** 사건, 수치, 역할 모두 연습용으로 만든 것이며 실제 장애와 무관하다.
