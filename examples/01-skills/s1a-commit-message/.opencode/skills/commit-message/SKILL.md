# 팀 커밋 메시지 규칙

스테이징된 변경(`git diff --staged`)을 읽고, 아래 규칙을 그대로 따르는 커밋 메시지 **한 개**를 만든다.
사용자가 "커밋까지 해줘"라고 명시하지 않는 한 `git commit`은 실행하지 않고 메시지만 보여 준다.

## 작업 순서

1. `git diff --staged`로 무엇이 바뀌었는지 읽는다. 스테이징된 변경이 없으면 "스테이징된 변경이 없습니다"라고 답하고 끝낸다(추측으로 쓰지 않는다).
2. `git branch --show-current`로 브랜치 이름을 본다. `fix/42-...`, `feat/105-...`처럼 슬래시 뒤에 숫자가 있으면 그 숫자가 이슈 번호다.
3. `git log -5 --oneline`으로 이 저장소가 평소 쓰는 scope 이름을 확인한다.
4. 아래 형식에 맞춰 메시지를 쓴다.

## 형식

```
type(scope): 요약

본문 (왜 바꿨는지)

Refs: #이슈번호
```

### 1행: `type(scope): 요약`

- 정규식으로 쓰면 `^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?: .{1,50}$`
- `요약`은 **50자 이내**, 한국어 가능, 마침표로 끝내지 않는다. "~했다"보다 "~수정", "~추가"처럼 명사형으로 끝낸다.
- `scope`는 바뀐 모듈·폴더 이름(영문 소문자, 하이픈 허용). 여러 모듈이면 가장 핵심인 하나만 쓴다.

### 허용 type

| type | 쓰는 때 |
| --- | --- |
| feat | 사용자가 체감하는 새 기능 |
| fix | 버그 수정 |
| docs | 문서만 변경 |
| style | 동작이 같은 서식·공백·세미콜론 정리 |
| refactor | 동작은 같고 구조만 개선 |
| perf | 성능 개선 |
| test | 테스트 추가·수정 |
| build | 빌드 스크립트, 의존성 |
| ci | CI 설정 |
| chore | 위에 해당하지 않는 잡무 |
| revert | 이전 커밋 되돌리기 |

위 표에 없는 type(`feature`, `bugfix`, `update` 등)은 쓰지 않는다. 코드와 테스트가 함께 바뀌었으면 코드 쪽 type(`fix`, `feat`)을 쓴다.

### 본문

- 1행 다음에 **빈 줄 한 개**를 둔다.
- 무엇을 바꿨는지는 diff에 이미 있으므로, **왜 바꿨는지**(문제 상황, 원인, 선택한 방법)를 2~4줄로 쓴다.
- 한 줄은 72자 안팎에서 줄바꿈한다.

### 꼬리말

- 본문 다음에 빈 줄 한 개를 두고 `Refs: #<이슈번호>` 한 줄을 쓴다. 예: `Refs: #42`
- 이슈 번호는 브랜치 이름 → 사용자가 말한 번호 순으로 찾는다. 둘 다 없으면 번호를 지어내지 말고 `Refs: #?`로 두고, 답변 끝에 "이슈 번호를 알려 주세요"라고 덧붙인다.

## 답변 형식

완성된 메시지를 코드 블록 하나에 담아 보여 주고, 코드 블록 밖에는 한두 문장 이내의 부연만 쓴다.
